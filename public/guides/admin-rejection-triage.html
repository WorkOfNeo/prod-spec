Triaging a rejection

A reviewer rejects something, or a customer sends an edit. Before anyone touches anything, work out which of four kinds it is — because each has a different owner, a different cost, and a different way of going wrong.

Admins only · start from Settings ▸ Rejection log. This guide is the human version of the same question the rejection-query tool answers.

1 The four answers

Every rejection and every customer edit lands in exactly one of these. Getting the bucket right first is most of the work — the wrong bucket sends a two-minute layout tweak to a developer, or sends an unfixable request to an agent that will confidently produce something wrong.

KindWhat it meansThe one-line testWho does it
1 · Output edit The layout is wrong: something is missing, misplaced, mis-sized or in the wrong language. The system can already print it. Could you fix it by editing the layout in the Output Builder, without new code? You, in the builder. Or Claude, against a named layout id.
2 · Needs code The capability doesn't exist, or exists and is broken. A control that isn't there; a token that renders empty though it's placed and the data is present. Is the thing being asked for absent from the app, or present-but-wrong? Claude, in a worktree, with a test.
3 · Human touch A judgement, a negotiation, or a decision only you can make. Which of two drafts is the keeper; what a customer will accept; whether to publish. Would two competent people reasonably disagree, with no fact in the repo settling it? You. Don't delegate it.
4 · Missing artwork The correct format lives outside the app — an email attachment, an Excel sheet, a supplier PDF, a customer's own template. Does the comment say "as per the attached", "sent through your mail", "on excel sheet"? You, to fetch the file. Then it becomes 1 or 2.
Bucket 4 is the one that wastes the most time

An agent cannot author against a file it has never seen. When a comment points at an attachment, no amount of reading the codebase will recover what the customer actually wants — and a confident guess ships wrong artwork to a supplier. Fetch the file first; the task is blocked until you do.

2 First, consolidate — never triage ticket by ticket

A rejection pile is far smaller than it looks. Reviewers paste near-identical text with tiny wording changes, and each per-size variant raises its own ticket, so one complaint becomes dozens of rows. Group before you read.

1Take the tickets for the POs in question. Note poNumber is stored as C-PO12345, so match on the bare number.
2Group by the comment, normalised — lowercase it, collapse whitespace, truncate. That collapses "as per mentioned Monday style wise" and "as per the mentioned as Monday style wise" into one complaint.
3Per group, look at: ticket count, status set, which POs, how many distinct styles, the docTypes, and — most important — the distinct layout ids (split the variantKey on #, since per-size variants look like layout:cmqt7…#110116).
4Read one verbatim sample per group. Never a paraphrase — the reviewer's exact words carry the answer more often than not.
What it looks like before raw
SOK, five POs: 84 tickets, all OPEN. Unreadable as a list — page after page of the same sentence against different sizes and colours.
What it looks like after grouped
Those 84 rows are four phrasings of one complaint, on one layout. Ge-kås's 184 tickets collapse to about ten real complaints across four layouts plus the cover page.
Grouping by layout is what turns tickets into work

A complaint is fixable per layout, not per ticket or per PO. Once a group names one layout id, you have a unit of work with a clear owner. Once it names four, you have four tasks pretending to be one — which is exactly how a task ends up scoped to a quarter of its real size.

3 Then run the three checks

For a group of tickets that says something is missing or wrong on a printed document, these three checks decide the bucket. Do all three before concluding — the expensive mistakes all come from stopping after one.

CheckQuestionHow to answer it
AIs the token on the layout?Open the layout and look for the token — {{price}}, {{barcode:ean13}}, whatever is said to be missing. Not there → output edit.
BIs the data on the style?Check the style's Monday data for the field behind that token. Empty → not a layout problem at all; it's a data gap, and the readiness gate should have caught it.
CDoes the comment point outside the app?"as per the attached format", "shared through your mail", "on excel sheet". Yes → missing artwork. Stop and fetch it.
A no → OUTPUT EDIT B no → DATA / HUMAN C yes → MISSING ARTWORK A yes + B yes + still blank → CODE BUG
The last row is the valuable one

Token placed, data present, and the PDF still shows nothing: that is a bug, and it is the single most worthwhile thing to hand to Claude — the diagnosis is sharp, the fix is testable, and it usually reaches far more styles than the POs that were rejected. It is also the case most often misfiled as "just edit the layout", where someone re-places a token that was never the problem.

4 Four real cases, worked

All from 12–13 August 2026. Each one was initially filed as a different kind than it turned out to be.

▾SOK · price stickers84 tickets, all OPENCODE
Complaint: "The retail price is missing on this layout PDF. Could you please add the price as per mentioned Monday style wise." — four phrasings, one layout.
Check A: the layout already places {{price}}. Check B: all 21 styles have a real Monday price — 19.95, 14.95, 26.95 — in a format the parser accepts. Check C: no attachment referenced.
Verdict: code bug in the render path. Would have been misfiled as an output edit by anyone who stopped after reading the comment.
▾Netto DK · wash care label14 ticketsOUTPUT EDIT
Complaint: "Could you please add the EAN barcode on care label front page."
Check A: the barcode token exists on the layout — but on a later sheet. So nothing is missing; it is placement.
Verdict: output edit. Note the physical constraint: a crowded front sheet may not hold an EAN-13 at its declared size, and shrinking one until it fits produces a barcode that won't scan. "It doesn't fit" is a legitimate answer.
▾Netto DK · carton marking4 tickets, OPENSTALE
Complaint: "Could you please add the customize button for this. Because the two styles are packed into the same carton."
Check: the layout already has multipleStyles on, which is what makes that button appear. The fix had already shipped.
Verdict: a fifth outcome the four buckets don't name — the ticket describes a state that no longer exists. It needs regeneration and closing, not work. Always check this before starting.
▾Ge-kås · five POs "wrong template"184 tickets, 156 OPENMIXED
Filed as: one problem — the care label used another retailer's template.
Actually: the care-label group is about a quarter of it. Another 35 open tickets say "The layout PDF template is incorrect. Please correct as per the attached format" against three other layouts — price sticker, price sticker (sets) and carton marking — plus separate cover-page complaints.
Verdict: the care-label half was a code/data fault (a cross-customer clone). The rest is bucket 4: the correct formats are in email attachments and an Excel sheet. Nothing can proceed on those until the files arrive.

5 Traps that make you classify it wrong

  • 1A draft layout prints nothing. Only published layouts are loaded at render time. A layout left in draft after an edit doesn't print the old version — the output disappears entirely, which looks like a completely different bug. If an output has gone silent, check its status before anything else.
  • 2Duplicating a layout copies its owner. A duplicate carries the source's customer and business area, and nothing warns when a spec ends up declaring another customer's row. That is how one retailer's website printed on another's labels across 109 styles. After any duplicate: re-point the owner, rename it, re-author it, then confirm no two layouts share the same definition.
  • 3The PO on the task may not belong to the customer on the task. One recent task listed four POs under a customer's name; one of them belonged to a different customer entirely and had already been resolved. Trust the ticket's own customer field, not the task title.
  • 4Re-rejections append, they don't duplicate. Rejecting again after a fix reopens the same ticket and appends the new comment with a — re-rejected <date> — separator. So one ticket can hold two different complaints, and the newest one is at the end. Read to the bottom.
  • 5A fixed problem leaves its tickets open. Shipping the fix doesn't close anything. Open tickets are a record of what was true when a reviewer looked, not of what is true now.

6 What to hand over, per bucket

Once the bucket is settled, this is what actually unblocks the work.

1 · Output edit

  • The layout name or id from the ticket group — not the PO.
  • What should change, and on which sheet or page.
  • Whether the layout is published or draft right now.
  • Whether it is shared with another business area, so the edit reaches more than you expect.

2 · Needs code

  • The result of checks A and B — that is the whole diagnosis.
  • One real style to reproduce against, with its PO.
  • The verbatim complaint, grouped, with counts.
  • Say explicitly that regeneration and supplier push are not in scope.

3 · Human touch

  • Name the decision as a question with options, not as a task.
  • Typical ones: which of two drafts is the keeper; a sheet size where two sources disagree; whether two business areas share one layout or get their own; whether to publish.
  • Everything downstream stays blocked until it is answered — so answer it first, not last.

4 · Missing artwork

  • The file itself — the attachment, the Excel sheet, the customer's template.
  • Which layout it is the reference for.
  • Whether it is artwork to reproduce or an annotated reference. Annotated drawings must never ship to a supplier as artwork.
The single highest-value sentence to write down when handing anything over: what you already checked and ruled out. It is what stops the next person re-deriving the same three facts — and it is the difference between a fix that lands in an hour and one that takes a day.
