Checking an order’s supplier folder

Type a PO number and the app reads the supplier’s folder for that order, tells you what looks wrong, and shows you everything it looked at. Two checks: cover pages that don’t belong, and files whose name has drifted. The same check can also be run across every order at once — section 6.

Checks in the sidebar, just under Delivery. Open to reviewers and admins alike. Check every PO, top right, is the fleet-wide version.

1 What this page asks that Delivery doesn’t

The two pages read the same folder from opposite ends, and that is why they are two pages.

Delivery

  • Starts from what we owe the supplier.
  • Asks: did everything arrive?
  • A stray file is, at most, one anonymous number.

Checks

  • Starts from what is actually in the folder.
  • Asks: is anything in here that shouldn’t be, or under the wrong name?
  • Names the file, says which style it answers to, and offers a remedy.
The folder belongs to the order, not to one style

A purchase order gets one folder, shared by every style on it — and most POs carry several styles. So both checks resolve the whole order before they judge a single file. Judging a file against one style’s expectations would propose removing its neighbour’s artwork.

2 Running a check

One field. Type the PO number, press Run checks, and wait a moment while the folder is read — it is several round-trips to SharePoint, so it isn’t instant.

5 Deleting safely

This is the only screen in the app that removes a file from a supplier’s folder, and a deletion there has no undo we control. So the safeguards are built into how it works, not into how carefully you click.

Deletes are listed first and separately from renames, and never folded together: one of the two is reversible and the other is not.

What the app guarantees when you press confirm

It re-reads the folder first. Nothing is acted on from the report you were shown. The check runs again against the live folder, and every file you ticked is validated against that.

Anything that changed is refused. A file renamed since the scan, or one the fresh check no longer flags, is left alone and reported back to you as refused — never acted on.

Only flagged rows, only the offered action. A file in the “looks right” group cannot be acted on at any price. A rename can only ever go to the one name the check resolved from the layout — you don’t get to type a name.

Files only, and only inside APPROVED LAYOUTS. The app has never written anywhere else. The PO folder above it holds the order’s own paperwork, which belongs to the customer and the supplier — those files are reported and never offered a button. Folders are never touched.

Nothing happens on its own. Nothing is on a schedule, and there is no “repair all”. A person picks the rows and confirms them by name, every time, and at most 100 files in one go. The fleet-wide sweep in section 6 finds work across every order but cannot do any of it — repairs only ever happen here, one folder at a time.

Every attempt is recorded — including the refusals and the failures, with the verdict you were shown, and who did it.

Afterwards, What happened lists the outcome file by file, and the report you are looking at is re-read so it can never show a picture that predates its own changes. Further down, What this page has already changed on this PO is the history for that order — there so that the person about to delete something can see what has already been removed, and by whom.

6 The same check, across every order

One folder at a time answers “is this order tidy?”. It never answers “how much of this is there, across the book?” — and that is the question worth planning around. Check every PO, the button at the top right of this page, runs the very same check on every purchase order in scope and collects what it finds in one place.

The sweep never touches a file

It renames nothing and deletes nothing. There is no button on it that could — not per file, not per group, not “fix all 142”. Its entire job is to tell you which folders are worth opening.

That is not caution for its own sake. A sweep’s findings are hours old by the time you read them, and colleagues rename things. Acting on a finding means opening that PO’s own check, where the folder is read live and every file is confirmed by name before anything happens — all the safeguards in section 5, unchanged. A bulk repair straight off a scan would be acting on a picture of the past.

It survives being interrupted

The list of orders is written before the work starts and each one is ticked off as its folder is checked, so nothing lives only in memory. If the app is deployed mid-run the sweep stops and the page says Interrupted — resumable: Resume picks up the orders it never reached and keeps everything it had already found. Stop ends a run early and keeps its findings too.

Scope: every purchase order at or above the supplier-send cutoff — the same orders whose documents actually leave the building. The number in force is shown on the page while a sweep runs.

7 When the folder can’t be read

No folder, no findings

If SharePoint refuses, throttles, or the order’s folder can’t be identified, the page tells you so and shows no checks at all. That is deliberate: a page saying “everything in this folder is unrecognised — delete?” during a brief outage would be actively dangerous. A failed lookup is never treated as evidence that a file is missing or wrong.

A good habit: run Checks on an order once its documents are approved and delivered. The flagged group tells you what to fix; the “files that look right” group tells you the check actually saw the folder. If a rename is offered, take it — it is the same file with the right name, and it never re-arms a supplier email. Once in a while, run Check every PO instead: it will not fix anything, but it tells you where the work actually is.
