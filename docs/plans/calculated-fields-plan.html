1The problem

The Netto DE – Private Label – Carton Marking layout needs a Total — the total pieces in the carton. Today a layout line can only print a token's raw value: {{qtyPerCarton}} prints one style's qty-per-carton and that's it. There is no way to:

  • Sum across styles — with the "Multiple styles" carton setting, a box can carry the base style plus up to 7 siblings ({{style2QtyPerCarton}}…), and the Total should be the sum of all of them. A single-style carton's Total is just its own qty.
  • Do any arithmetic at all — multiply, divide, count, round. Every future "computed" field (total pcs across a numbered carton set, pcs per inner × inners, etc.) hits the same wall.

So rather than adding a one-off {{totalQty}} token, the plan is a small, safe expression token that composes the tokens we already have. The Netto DE Total becomes its first user.

2How tokens work today (30-second recap)

Every builder layout renders through one pipeline (src/lib/output-layouts/):

line text→ conditionals
{{if …}}…{{endif}}→ token substitution
{{qtyPerCarton}} → "48"→ HTML → PDF
  • schema.ts — grammar (TOKEN_RE, IF_RE), shared conditional evaluation.
  • tokens.ts — server resolvers mapping each token onto StyleData (qtyPerCarton = carton.outerVE), plus readiness (which mapped columns a token needs) and the "unresolved tokens" amber-chip list.
  • token-meta.ts — client-safe metadata: builder palette, publish validation. Sibling tokens ({{style2QtyPerCarton}}) are recognised by pattern; slots ≥ 2 only resolve when StyleData.multipleStyles is set (a one-off carton-dialog print with siblings picked).
  • render.ts — the one renderer for preview and production.

Conditionals already prove the pattern we'll follow: a second grammar alongside plain tokens, evaluated per line, with its evaluation logic shared between the renderer, readiness, and the builder's validation.

3Proposed design: the {{= …}} calculated token

A new inline token, mirroring how conditionals are structured — one line, evaluated before plain-token substitution:

The Netto DE "Total" line
Total:   {{= sum(qtyPerCarton) }} PCS

Single-style carton → 48 PCS. Multi-style print with two siblings (48 + 24 + 12) → 84 PCS. Same line, no conditionals needed.

Grammar (v1 — deliberately small)

ElementMeaningExample
Field identifiersAny known text token key, resolved via the existing resolvers and parsed as a number. Sibling slot keys work too.qtyPerCarton, cartonTotal, style2QtyPerCarton
Operators+ − × ÷ and parentheses, numeric literals{{= qtyPerCarton * cartonTotal }}
sum(field)Sum of field across every style on the carton (base + active siblings; see §4){{= sum(qtyPerCarton) }}
count(field)How many styles on the carton have a non-empty field{{= count(styleNumber) }} → styles on the box
min(field) / max(field)Smallest / largest value across styles{{= max(qtyPerCarton) }}
round(expr, n)Round to n decimals (default 0). Otherwise integers print bare, fractions print trimmed.{{= round(qtyPerCarton / 12, 1) }}

Implementation: a ~100-line recursive-descent parser/evaluator in a new client-safe module — no eval, no dependencies. The same parsed AST powers rendering, validation, and readiness, so they can never disagree (the same principle applyConditionals already follows).

Why this shape and not the alternatives

OptionVerdict
Inline {{= expr }} (proposed)✅ Flexible, self-documenting in the line where it prints, mirrors the existing conditional grammar, zero new UI surfaces required to be useful.
One-off tokens ({{totalQty}})❌ Solves only today's field; next calculation needs another code deploy.
Named calculated fields defined in the layout's Settings card, referenced as {{myField}}⏸ Nice for reuse, but adds a Settings editor, name-collision rules, and indirection. Can be layered on later — expressions are the primitive either way.

Grammar safety: {{= …}} cannot half-match the existing strict TOKEN_RE (which requires a letter after {{), so it gets its own regex — exactly how {{if …}} avoids collisions today. Existing layouts are untouched.

4Multi-style & empty-value semantics

Which styles do aggregates see?

Aggregates iterate the same slots the sibling tokens already use (siblingForSlot in tokens.ts):

  • Standard generation (multipleStyles flag off): slot 1 only — sum(qtyPerCarton) ≡ the base style's own qty. Standard outputs are byte-identical in behaviour to a plain total.
  • Multi-style carton print (operator picked siblings in the carton dialog): slot 1 + each picked sibling. Sibling slots that are empty are simply skipped — an unfilled slot is not a data gap, matching how {{style3}} renders empty today.

This reuses the existing gate, so calculated fields can never leak sibling data into standard generation.

Missing styles never break an equation

A hard requirement: an expression that mentions style 2 (or 3, 4…) must not fail when that slot is empty. Two ways to get there, both supported:

Implicit — the recommended way
{{= sum(qtyPerCarton) }}

sum() walks the slots that are actually filled. No style 2 → it contributes nothing. You never have to say "if style two" — the aggregate is the if.

Explicit — direct slot references are safe too
{{= qtyPerCarton + style2QtyPerCarton + style3QtyPerCarton }}

An empty sibling reference coerces to 0 inside an expression — the equation still evaluates. Only an empty base-style field (a real data gap, e.g. no carton qty mapped) makes the calc unresolved.

When is a calc "unresolved"?

SituationResult
All referenced base-style fields resolve to numbersPrints the value
A referenced base field is empty (e.g. no carton qty mapped)Whole calc resolves empty → line-drop rules apply in production; amber chip = sum(qtyPerCarton)? in preview — same behaviour as a plain empty token
A referenced field resolves to non-numeric text (e.g. sum(colourName))Caught at build/publish time by validation where possible (field kind check); at render time a non-numeric value counts as empty
An empty sibling slot — inside sum()/count() or referenced directly (style2QtyPerCarton)Skipped / counts as 0 — never a gap, never an error

Composing with {{if …}} conditionals

Conditionals evaluate first, calcs second, plain tokens last — so a calc inside a conditional branch only runs when that branch is taken. This is guaranteed by the pipeline order and covered by tests:

{{if …}} branches picked→ {{= …}} evaluated→ tokens substituted
Example — different equation per mode
{{if multipleStyles == true}}Total: {{= sum(qtyPerCarton) }} PCS{{else}}Qty: {{qtyPerCarton}} PCS{{endif}}

Multi-style print → the summed Total; standard print → the plain per-style qty line. And because conditionals can already check sibling fields, {{if style2 != ""}}…{{endif}} works for showing a whole line only when a second style is on the box.

Nesting a conditional inside an expression ({{= if(…) }}) is deliberately out of scope for v1 — the branch-outside/calc-inside pattern above plus 0-coercing sibling refs covers every case we've seen, without inventing a second conditional syntax.

Readiness (the "ready to generate" gate)

Fields referenced inside an expression contribute their mapped columns exactly like the bare token would: sum(qtyPerCarton) ⇒ requires the cartonQty column, via the existing REQUIRED_COLUMNS table. Sibling references contribute nothing (they depend on other styles, mirroring current sibling-token rules).

6Applying it to Netto DE – Private Label – Carton Marking

  1. After the code ships, edit the layout in the builder (targeted edit — never a re-run of a create/upsert script, per the layout-guide gotcha) and set the Total line to Total: {{= sum(qtyPerCarton) }} PCS (exact label per the approved artwork).
  2. Confirm the layout's Settings have Multiple styles enabled so the carton dialog offers siblings and the sum can go multi-style.
  3. Render a proof on a real style (0 unresolved), then a multi-style carton-dialog print with 2–3 siblings, and eyeball both against the approved artwork before publishing.

7Testing & verification

  • Unit — parser/evaluator (tests/): literals, precedence, parentheses, each function, division by zero → empty, malformed syntax → precise error strings, unknown identifier rejection.
  • Unit — resolver integration: sum(qtyPerCarton) on a single-style StyleData, on a multi-style one with 2 siblings, with an empty sibling slot, with a missing base value (→ unresolved); direct style2QtyPerCarton reference with no style 2 → coerces to 0, never errors; readiness columns include cartonQty; unresolvedTokens lists the calc when the base input is missing.
  • Unit — conditional composition: a calc inside {{if multipleStyles == true}}… only evaluates in the taken branch; {{if style2 != ""}} gating a calc line renders it exactly when a sibling is picked.
  • Render proof: buildSampleStyleData() → renderLayoutHtml → PDF for a layout using the Total line, in both single and multi-style mode (the same path the guide's "verify before publish" prescribes).
  • Regression: an existing published layout renders byte-identically (no calc syntax present → new pass is a no-op).

8Rollout, risks, phases

Deploy-before-edit: a layout line using {{= …}} only renders once the matching app version is live — on an older version the text would print literally. Same known gotcha as the per-side pad field: ship the code first, edit the Netto DE layout second. The publish gate on old versions would reject the syntax anyway, which is the correct failure mode.

  1. Phase 1 — core engine (the bulk of this plan): calc module, resolver/readiness/render integration, publish validation, tests, docs. Delivers sum(qtyPerCarton) end-to-end.
  2. Phase 2 — builder UX: palette group, canvas highlighting, live per-line errors. Small, ships with or right after Phase 1.
  3. Phase 3 (optional, later): named calculated fields in Settings for reuse across blocks; calcs in fileName; more functions (e.g. per-size aggregates) as real layouts demand them.

Risks & mitigations: expression bugs are contained to layouts that opt into the syntax (regression-safe by construction); the evaluator is pure and dependency-free (no injection surface); validation runs client-side and at the publish gate so broken expressions never reach production PDFs.
